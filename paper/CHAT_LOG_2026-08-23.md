## Random Hadamard transform

The intended term is Random Hadamard Transform (RHT). The transform used in
NVIDIA's NVFP4 pipeline is:

\[
R_d = S_d H_d / \sqrt d,
\]

where a fixed random Rademacher sign vector is shared across layers. NVIDIA's
implementation uses tiled H16 RHT on BF16 operands associated with Wgrad.

Our original standalone kernel begins at H256, so a separate tiled H16
prototype was implemented rather than claiming that the H256 API directly
matches the NVFP4 use case.

### H16 prototype

- Fixed sign mask: `0xA3F5`
- Operation: `x @ (S @ H16 / 4)`
- Workload: 4,194,304 rows, 67,108,864 elements
- Correctness: exact match at FP16/BF16 output dtype

| Input | Triton RHT | Dense H16 matmul | Relative result |
|---|---:|---:|---:|
| FP16 | 0.1615 ms | 0.1579 ms | 0.978x |
| BF16 | 0.1615 ms | 0.1579 ms | 0.978x |

### Fused RHT + FP8 prototype

Hopper pipeline:

```text
FP16/BF16 input
  -> fixed random sign
  -> normalized H16
  -> per-16 amax and scaling
  -> E4M3 output
```

| Input | Fused | Eager separate operations | Speedup |
|---|---:|---:|---:|
| FP16 | 0.262 ms | 1.578 ms | 6.01x |
| BF16 | 0.264 ms | 1.580 ms | 5.98x |

- FP16 reconstruction MSE: approximately 0.000498.
- BF16 reconstruction MSE: approximately 0.000505.
- This is a preliminary fusion ablation against eager PyTorch composition.
- It is not yet a Transformer Engine comparison.
- It is not native NVFP4; H100 lacks native NVFP4 execution.

## Transformer Engine decision

Transformer Engine does not require NVFP4 for useful benchmarking on Hopper.
H100 can benchmark:

- BF16 `te.Linear`
- FP8 CurrentScaling
- FP8 DelayedScaling
- FP8 Block Scaling
- Fprop, Dgrad, Wgrad, and complete forward/backward time
- Autocast timing versus pre-quantized GEMM timing

Transformer Engine's production RHT is coupled to the NVFP4 recipe and does not
have a documented public standalone RHT API. The direct native comparison must
therefore be run on Blackwell:

```text
TE NVFP4 + RHT
TE NVFP4 with RHT disabled
TE NVFP4 with/replacing RHT using our implementation
```

On H100, the correct application framing is RHT-augmented FP8, not NVFP4.

## Hardware support boundary

- H100/H200 Hopper: native tensor-wide FP8 and FP8 Block Scaling.
- MXFP8: native SM100+ Blackwell.
- NVFP4: native SM100/SM103 for training.
- H100 can emulate the numerical dataflow but cannot support native MXFP8 or
  NVFP4 performance claims.

## Claims currently safe to make

- On H100, the standalone kernel operates near the empirical memory roofline.
- It is competitive with all tested baselines and wins substantially at large
  transform sizes.
- It executes 2.02--3.60x fewer dynamic warp instructions than HadaCore at the
  profiled points.
- A preliminary fused H16 RHT--FP8 Hopper prototype is approximately 6x faster
  than eager separate operations.

Claims not yet safe:

- Faster than every baseline at every transform size.
- Native NVFP4 acceleration on H100.
- A 6x win over Transformer Engine.
- End-to-end training speedup or unchanged convergence.
